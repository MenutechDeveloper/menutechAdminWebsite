1. ESTADO ACTUAL DE LA CONFIGURACIÓN DEL CRON EN LEARN.HTML
-------------------------------------------------------------------------------
Actualmente, en `docs/learn.html`:
- La interfaz de usuario utiliza un menú desplegable rígido (<select id="auto-schedule-interval">) con las siguientes opciones predefinidas:
  * 0 minutos (En Demanda / Manual / Webhook)
  * 15 minutos (Cada 15 minutos)
  * 60 minutos (Cada hora)
  * 1440 minutos (Cada 24 horas - Diario)
  * 10080 minutos (Cada semana)

- En la función de generación de código JavaScript (`generateDeterministicTypeScript`), el tiempo se evalúa mediante un bloque `if / else if` estricto que convierte esos minutos a un texto explicativo para la cabecera del archivo:
  * 15  => "Cada 15 Minutos (*/15 * * * *)"
  * 60  => "Cada Hora (0 * * * *)"
  * 1440 => "Diario / Cada 24 Horas (0 0 * * *)"
  * 10080 => "Semanal (0 0 * * 0)"

DIAGNÓSTICO SOBRE OPCIONES PREDEFINIDAS VS. TIEMPOS LIBRES:
Actualmente NO es posible que el usuario ingrese tiempos personalizados como "3 minutos", "2 segundos" o "1 año". Si el usuario requiere esa flexibilidad, el `<select>` actual limita la experiencia. Para que funcione libremente, se requiere cambiar el `<select>` por un campo de texto o selecciones compuestas (Número + Unidad: segundos, minutos, horas, días, años) o permitir expresiones Cron directas (* * * * *).


2. SOBRE LA GENERALIZACIÓN DEL CRON POR ALGORITMO
-------------------------------------------------------------------------------
¿ES CORRECTO TENER UN CRON GENERALIZADO / INDIVIDUAL PARA CADA ALGORITMO?
SÍ, ES TOTALMENTE CORRECTO Y CORRESPONDE A LA MEJOR PRÁCTICA DE ARQUITECTURA.

Razones técnicas:
- Cada algoritmo o Edge Function cumple un propósito distinto y requiere su propia frecuencia de ejecución (ejemplo: un algoritmo de "Reporte Diario de Ventas" debe ejecutarse cada 24 horas, mientras que un algoritmo de "Alertas de Stock Bajo" podría requerir ejecutarse cada 5 minutos o 30 segundos).
- En Supabase y arquitecturas Serverless, cada función es un componente independiente que se activa de forma aislada.

CÓMO FUNCIONA EL CRON EN SUPABASE EDGE FUNCTIONS:
Una Edge Function en Supabase es un servidor HTTP en Deno (`Deno.serve`). Por sí sola, la función NO tiene un bucle interno ni un temporizador propio corriendo en segundo plano. Para que la función se ejecute automáticamente cada cierto tiempo, Supabase ofrece dos mecanismos:

a) pg_cron + pg_net (Desde la base de datos PostgreSQL):
   Se crea una tarea en PostgreSQL que realiza una petición HTTP POST a la Edge Function (`https://<project-ref>.supabase.co/functions/v1/<slug>`) según el horario programado.
   Sintaxis SQL habitual:
   SELECT cron.schedule('nombre-job', '0 * * * *', $$
     SELECT net.http_post(
       url:='https://<tu-proyecto>.supabase.co/functions/v1/mi-algoritmo',
       headers:='{"Content-Type": "application/json", "Authorization": "Bearer SERVICE_ROLE_KEY"}'::jsonb
     )
   $$);

b) Configuración del CLI de Supabase (`supabase/config.toml`):
   Supabase permite declarar la programación directamente en el archivo de configuración:
   [functions.mi-algoritmo]
   verify_jwt = false
   schedule = "0 0 * * *"  # Expresión Cron


3. EVALUACIÓN DEL CÓDIGO TYPESCRIPT GENERADO
-------------------------------------------------------------------------------
¿EL ALGORITMO GENERA EL TYPESCRIPT COMPLETO DE LA FUNCIÓN?

LO QUE SÍ GENERA CORRECTAMENTE (100% FUNCIONAL COMO HTTP EDGE FUNCTION):
1. Importación de módulos Deno/Supabase (`serve` de `std/http/server.ts` y `createClient` de `@supabase/supabase-js`).
2. Cabeceras CORS completas (`Access-Control-Allow-Origin: *`, `Access-Control-Allow-Headers`) y manejo de solicitudes Preflight `OPTIONS`.
3. Conexión segura a Supabase mediante variables de entorno (`Deno.env.get("SUPABASE_URL")` y `SUPABASE_SERVICE_ROLE_KEY`).
4. Iteración y ejecución determinista de los bloques configurados (Fuente de Datos desde `menutech_knowledge`, Instrucciones/Reglas, Reacciones de IA y Eventos).
5. Captura y manejo de excepciones mediante `try / catch` retornando JSON estandarizado con códigos de estado HTTP `200` y `500`.
6. Encabezado informativo en comentarios con el Slug único de la función y comandos CLI de despliegue (`supabase functions deploy <slug> --no-verify-jwt`).

LO QUE LE FALTA RESPECTO AL CRON Y TIEMPOS LIBRES:
1. Formato de Tiempos Libres:
   Actualmente el código generado sólo estampa el tiempo como comentario estático en la cabecera si coincide con las 4 opciones numéricas del `<select>`. No calcula ni traduce tiempos libres (ej. "3 minutos" -> `*/3 * * * *`, "2 segundos" -> frecuencia rápida, "1 año" -> `0 0 1 1 *`).

2. Automatización del Trigger/Disparador del Cron:
   Aunque el comentario indica cada cuánto debe ejecutarse, el código TypeScript generado no genera el bloque SQL auxiliar para registrar el job en `pg_cron` ni la directiva `schedule` para el `config.toml` de Supabase.


4. CONCLUSIÓN Y RECOMENDACIONES
-------------------------------------------------------------------------------
1. **Estructura del Código TypeScript**: Está muy bien estructurada, limpia y sigue los estándares de Deno / Supabase Edge Functions.
2. **Generalización del Cron**: Es correcta por diseño. Cada algoritmo debe tener su propio intervalo programado.
3. **Ajustes Sugeridos (Para futuras actualizaciones cuando lo solicites)**:
   - Reemplazar el `<select>` rígido por campos flexibles de entrada de tiempo (Número + Unidad: Segundos, Minutos, Horas, Días, Meses, Años) o un campo de expresión Cron.
   - Incluir en el modal de código generado la sentencia SQL de `pg_cron` o la directiva `config.toml` para que la programación del tiempo sea 100% automatizable en Supabase.
